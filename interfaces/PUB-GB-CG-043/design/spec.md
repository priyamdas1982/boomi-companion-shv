## Process design

Start shape: Web Services Server listen, using operation C3, exposed through API Service component C2.

Main path (TC-A, TC-T and TC-F are the labels for the three Try/Catch shapes; BR-K, BR-F and BR-A are the three Branch shapes; BR-K is new in revision 9).

**Revision 8 structure (user, Q1: "b").** TC-A no longer sits straight after Start. It now wraps only the valid-body path (the Kafka send and the 202). The functional-error path (TC-F, BR-F) is outside TC-A. S1 and the Decision sit between Start and the split, outside every Try/Catch, because anything inside TC-A's try path, including the Decision's False branch, would be in TC-A's scope. Order on the canvas: Start -> S1 -> Decision -> True: TC-A -> TC-T -> ...; False: TC-F -> ...

1. **Start** (WSS listen, C3).
2. **Data Process, Custom Scripting "Check JSON body"** (script S1): sets `DDP_VALIDATION_ERROR`. The document passes through unchanged. Outside every Try/Catch (revision 8). S1 is written so it never throws (see "Scripts"); if it threw anyway, the execution would fail unhandled with the runtime's default 500, which is an error and never a success.
3. **Decision "Body is valid JSON?"**: `DDP_VALIDATION_ERROR` equals empty. Outside every Try/Catch (revision 8). It compares a property only.
   - **True (valid)**: go to 4.
   - **False (functional error)**: go to 5.
4. Valid path (revision 5: the "Set Kafka header" step is removed. Revision 7 second pass: no retry-topic send; the catch path throws. Revision 8: TC-A starts here):
   0. **TC-A** Try/Catch "Technical error" (revision 7 second pass; was "Retry-topic send failure"), retry count 0, catch All errors. Its try path is steps 4.1 to 4.6 only. Its catch path is step 6.
   1. **TC-T** Try/Catch "Kafka send", **retry count 2** (3 attempts in total; user: "1a"; rows 22, 26), catch All errors. Its Try dragpoint goes to BR-K (4.2); its Catch dragpoint goes to 4.6.
   2. Try: **Branch BR-K "Send then accept"** (revision 9, row 30), 2 branches (`numBranches="2"`, dragpoints identifier 1 and 2, both wired). It is the first shape of the TC-T try path, so every TC-T retry re-runs it.
      - **Branch 1:**
        1. **Kafka Produce** (C4 + C7, topic `gb-cg.q.leads.in.insert`), body unchanged, no headers, no key. C7 outputs no document (8bee26c5).
        2. **Stop "Sent"**, `continue="true"` ("End and continue"). It only terminates the path (skill rule: end every path at a terminal shape); it normally receives no document. It must be `continue="true"`: `continue="false"` would end the whole process before branch 2 runs.
      - **Branch 2** (runs after branch 1 has completed):
        3. **Set Properties "Response 202"**: HTTP response status code 202.
        4. **Message "Accepted"**: `{"status":"accepted"}`. It replaces branch 2's copy of the request document.
        5. **Return Documents "Accepted"**.
      - **Success:** branch 1 sends and ends with no output and no error; branch 2 receives its copy of the request document and returns 202 `{"status":"accepted"}`. The HTTP response holds only that document (branch 1 returns nothing).
      - **Failed attempt:** C7 raises a document error on branch 1. The document is caught by TC-T, which encloses BR-K, so BR-K gives branch 2 no document and no 202 is built for that attempt (22c61363 pattern). TC-T then re-runs its try path from BR-K. If a retry succeeds, that retry's branch 2 returns the 202. If all 3 attempts fail, the document goes to 4.6.
      - **Why no other guard:** the TC-T catch path runs only after the try path (branch 2 included) has finished, so a property set there could not stop branch 2 (see "Changes in revision 9"). No Decision, process property or script is added.
   6. TC-T Catch (all 3 attempts failed): **Exception step "Kafka send failed"**, stop single document = true, message `Kafka send to gb-cg.q.leads.in.insert failed after 3 attempts: {1}`, parameter {1} = Meta information "Base - Try/Catch Message" (the last Kafka error). TC-A catches it and returns 500 with this text through BR-A (step 6). Nothing is sent to any other topic, and no 202 is returned (CLAUDE.md "Kafka send failures"). The C8 connector step and the steps "Response 202 (parked)", "Accepted (parked)" and "Accepted - parked on retry topic" are removed from C1.
5. Functional-error path (no Kafka send, no retry). Revision 8: outside TC-A (user: "b"):
   1. **TC-F** Try/Catch "Functional", retry count 0, catch All errors. It is the only Try/Catch on this path.
   2. Try: **Exception step "Functional error"** (stop single document = true), message = `DDP_VALIDATION_ERROR`. TC-F catches it, so the Try/Catch message holds the functional error.
   3. TC-F Catch: **Branch BR-F "Notify then reject"**, 2 branches (`numBranches="2"`).
   4. BR-F branch 1:
      1. **Set Properties "Set facade inputs"** (renamed from "Set DDP_MED_NS_Msg" in revision 7): `DDP_MED_NS_Msg` = Meta information "Base - Try/Catch Message" (`meta.base.catcherrorsmessage`), plus the facade inputs in "Facade inputs" (functional-error values where the table has per-path values).
      2. **Process Call** `[MED] (sub) CACHE Notification Facade` (C9), wait = true, **abort = true** (row 28; revision 8), no return paths. Branch 1 ends here. If the facade fails, the parent stops, branch 2 does not run (Boomi documentation, V7) and, because no Try/Catch encloses the TC-F catch path (revision 8), the execution fails unhandled straight away: facade tried once, caller gets the runtime's default 500 (user: "if facade fails, throw an exception. unhandled." and "b"; row 29).
   5. BR-F branch 2 (runs after branch 1 completes):
      1. **Set Properties "Response 400"**: HTTP status 400.
      2. **Message "Rejected"**: `{"status":"rejected","message":"<Try/Catch message>"}`. The `message` value comes from Meta information "Base - Try/Catch Message" and not from `DDP_MED_NS_Msg`, because a DDP set on branch 1 does not reach branch 2.
      3. **Return Documents "Rejected - functional error"**.
      An unexpected error in these three steps (not expected; fixed texts and a Meta information value) is not caught by any Try/Catch: the execution fails unhandled with the runtime's default 500 instead of a 500 JSON body. Accepted by the user with option "b" (row 29). The normal 400 is unchanged.
6. TC-A Catch: the Exception "Kafka send failed" from the TC-T catch path, or any other unexpected error in the TC-A try path (the valid-body path only, revision 8). TC-A is renamed "Technical error" (was "Retry-topic send failure"):
   1. **Branch BR-A "Notify then error"**, 2 branches (`numBranches="2"`).
   2. BR-A branch 1:
      1. **Set Properties "Set facade inputs"** (renamed in revision 7): `DDP_MED_NS_Msg` = Meta information "Base - Try/Catch Message", plus the facade inputs in "Facade inputs".
      2. **Process Call** `[MED] (sub) CACHE Notification Facade` (C9), wait = true, **abort = true** (row 28; revision 8), no return paths. Branch 1 ends here. If the facade fails, the parent stops, branch 2 does not run, and the execution fails unhandled: there is no Try/Catch around the TC-A catch path, so the caller gets the runtime's default 500 (user: "if facade fails, throw an exception. unhandled."; seen in 22c61363).
   3. BR-A branch 2 (runs after branch 1 completes):
      1. **Set Properties "Response 500"**: HTTP status 500, and DDP `DDP_ERROR_MESSAGE` = Meta information "Base - Try/Catch Message" (read on branch 2 for the same reason as the 400 path: a DDP set on branch 1 does not reach branch 2).
      2. **Data Process, Custom Scripting "Build error response"** (script S2): replaces the document with `{"status":"error","message":<DDP_ERROR_MESSAGE, JSON-escaped>}`. Replaces the revision 6 Message "Error" and its fixed text (user: "return exception to api consumer" and "2a"; row 27).
      3. **Return Documents "Error"**.

Each outcome ends in its own Return Documents shape: three in total ("Accepted", "Rejected - functional error", "Error"). No two outcomes converge on one step. Every Branch dragpoint is wired. The Process Calls have no outgoing connections because the facade returns no documents. BR-K branch 1 ends in Stop "Sent" (revision 9). There are no Notify shapes.

Shape count summary (revision 9): Try/Catch 3 (TC-A, TC-T, TC-F), **Branch 3 (BR-K, BR-F, BR-A)**, Process Call 2, Return Documents 3, Exception 2 ("Functional error", "Kafka send failed"), Decision 1, Data Process 2 (S1, S2), Kafka connector steps 1 (C7), Message 2 ("Accepted", "Rejected"), Set Properties 5 ("Response 202", two "Set facade inputs", "Response 400", "Response 500"), **Stop 1 ("Sent", continue = true)**, Notify 0. (Revision 8 had Branch 2 and Stop 0.)

Error reaches the caller on every path (user: "handled or unhandled"; revision 8 for the facade rows):

| Error | Handled by | Caller receives |
|-------|------------|-----------------|
| Functional (body missing, empty, not JSON, not an object) | TC-F, BR-F | 400 with the functional error text |
| Kafka send fails on all attempts | TC-T (retries), Exception, TC-A, BR-A | 500 with the exception text |
| Any other error in the TC-A try path outside TC-T's try path (not expected; revision 9: there is no such step, because BR-K and both its branches are on the TC-T try path) | TC-A, BR-A | 500 with the exception text |
| Unexpected error on BR-K branch 2 ("Response 202", "Accepted", Return Documents "Accepted"; not expected: fixed status and fixed text). Same placement as revision 8, where these steps were also on the TC-T try path | TC-T retries the try path from BR-K, so the lead may be sent again (up to 3 sends in total); then Exception "Kafka send failed" (text ends with that error), TC-A, BR-A | 500 with the exception text; never a 202 for that request |
| Facade fails on BR-A branch 1 | Not handled (user: "if facade fails, throw an exception. unhandled."). wait = true, abort = true: the parent stops and is marked failed; no Try/Catch encloses the TC-A catch path | Runtime default 500 for an unhandled failure (HTTP 500 page in 22c61363, not JSON). The facade error is in the Boomi process log |
| Facade fails on BR-F branch 1 | Not handled (user: "b", revision 8). The parent stops; no Try/Catch encloses the TC-F catch path; facade tried once | Runtime default 500, not JSON |
| Unexpected error on BR-F branch 2 ("Response 400", "Rejected", Return Documents) | Not handled (user: "b"; accepted side effect) | Runtime default 500, not JSON |
| Unexpected error in S1 or the Decision (before the split; not expected, S1 never throws) | Not handled; outside every Try/Catch (consequence of "b") | Runtime default 500, not JSON |
| Error inside BR-A branch 2 itself (S2 or Set Properties) | No enclosing Try/Catch | Runtime default 500 page (seen in 22c61363). S2 is written so it cannot throw |
| Runtime cancels the execution at its time limit | Cannot be caught (93e06b38) | No response. Prevented only by timing (rows 19, 26) |

Definitions:

- **Functional error**: the request body is missing or empty, is not valid JSON, or is not a JSON object. No other content validation is done, because validation is out of scope per the document. This is the orchestrator's follow-up C definition, and the user did not change it.
- **Technical error**: any error on the TC-T try path. In practice this is a Kafka produce failure on the main topic.
- **Unhandled by design (revision 8; user: "if facade fails, throw an exception. unhandled." and "b")**: a facade failure on either path, and any unexpected error outside TC-A's and TC-F's try paths (S1, the Decision, BR-F branch 2, BR-A branch 2).
